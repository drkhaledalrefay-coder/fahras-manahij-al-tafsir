## ٢. شرط المسابقة: «مسار إجابة من المصادر المعتمدة»

ورشة المسابقة (ضبط المحتوى) عرضت هذا المسار، والالتزام به **إلزامي**:

> سؤال ← استرجاع من الحزمة المعتمدة ← **هل الدليل كافٍ؟** ← نعم: صياغة مسندة وفحص المراجع ← اجتياز الفحص ← عرض الإجابة ومواضع الاستشهاد · لا / فشل التحقق ← **امتناع أو إحالة إلى المراجعة**.
> «وجود الاستشهاد لا يثبت صحة الاستنتاج وحده. تحقق من المطابقة والدلالة مع مراجعة مناسبة.»

ترجمته عندنا = **عقد إسناد فهرسة المنهج**:
نافذة من نص المصدر المثبّت ← حزمة أجزاء مرقّمة ← اقتراح وسوم وشواهد **بمعرّفات الأجزاء فقط** ← فحص حتمي للمصدر والحدود وكفاية الشاهد ← **مرشّح للمراجعة** أو **امتناع بسبب محدد وإحالة للمتخصص**. الاعتماد قرار المتخصص بعد فحص الدلالة.

## ٣. النماذج المقترحة (أقوى من `qwen2.5:14b`)

المبدأ لا يتغيّر: **وكيلان من عائلتين مختلفتين** (مصنّف + مدقّق إعادة تصنيف) + فاحص حتمي + عتبة اللجنة **٨٥** + امتناع عند الشك. ما يتغيّر هو حجم النماذج حسب ذاكرة الجهاز.

| ذاكرة المعالج الرسومي | المصنّف (عائلة Qwen) | المدقّق (عائلة مختلفة) | ملاحظة |
|---|---|---|---|
| **٤٨ غيغابايت فأكثر** | `qwen2.5:72b` | `llama3.3:70b` أو `gemma3:27b` | الأقوى محلياً؛ تشغيل متتابع لا متزامن |
| **٢٤ غيغابايت** (الأرجح) | `qwen2.5:32b` | `gemma3:27b` | **التوصية الافتراضية**: عربية قوية والتزام جيد بمخرجات JSON |
| **١٦ غيغابايت** | `qwen2.5:14b` (الخطة الأصلية) | `gemma3:12b` | الحد الأدنى؛ لا تُحمَّل معاً |

- **تحقق قبل السحب:** الأسماء أعلاه من مكتبة Ollama وقت كتابة الخطة؛ تأكد منها (`ollama pull <الاسم>`، ثم `ollama list`) و**اكتب الوسم الفعلي** في `committee.json` وفي العرض. لا تقل اسم نموذج لم يُشغَّل فعلاً.
- **السياق:** أطول نافذة في النور لها آلاف الحروف؛ ارفع `num_ctx` عند الحاجة (مثلاً ١٦٣٨٤)، واعلم أن الذاكرة تزيد.
- **الحرارة:** `temperature: 0` للمصنّف والمدقّق ولصياغة سبب الامتناع.
- **بديل سحابي (قرار المالك فقط):** المحوّل `src/classify_api.py` متوافق مع واجهة OpenAI، وجُرّب سابقاً مع `deepseek-chat`. المفتاح يُوضع **في متغير بيئة جلسة الطرفية فقط** (`LLM_API_KEY`) — **لا** في ملف ولا في git ولا في الشات. وإن استُخدم يُعلَن في العرض «تشغيل مستضاف» لا «محلي».

## ٤. خطوات التشغيل

1. **دمج المرحلة ٠** (القسم ٢) وتشغيل `python -m pytest -q`.
2. **تجربة عيّنة أولاً:** آية واحدة غنية بالتفاسير الأربعة — مثلاً **٢٤:٣٥ (آية النور)** — ثم توقّف:
   ```powershell
   # جلسة الطرفية فقط — لا تكتب المفتاح في ملف
   $env:LLM_API_KEY = "ollama"
   $env:LLM_BASE_URL = "http://localhost:11434/v1"
   python src/run_window.py --tafsir al_tabari --window 24_35_p01 --base data/nur/al_tabari --dry-run
   python src/run_window.py --tafsir al_tabari --window 24_35_p01 --base data/nur/al_tabari --api --model qwen2.5:32b
   ```
   (آية النور عند الطبري مقسّمة إلى أربع نوافذ `24_35_p01`…`24_35_p04`؛ شغّلها كلها. الأسماء الفعلية من `data/nur/<tafsir>/windows/`.)
3. **مراجعة العيّنة** (القسم ٥) قبل أي تشغيل جماعي.
4. **التشغيل الجماعي** لكل تفسير: `python src/run_surah.py --db "<path>/quran.db" --tafsir <t> --surah 24 --base data/nur/<t> --classify --time-cap 300`، ثم المدقّق من العائلة الثانية، ثم الرئيس الحتمي.
5. **التسجيل:** commit لكل تفسير بعد اجتياز البوابات، برسالة فيها اسم النموذج الفعلي وتاريخ التشغيل (يُقيَّم فقط ما أُنجز ٤–٦ أكتوبر).

## ٥. المراجعة بعد الوسم (Claude وCodex) — بلا تساهل

- **عيّنة عمياء:** ١٠ نوافذ على الأقل لكل تفسير. نموذج من عائلة **ثالثة** يعيد الوسم دون أن يرى وسوم المصنّف، ثم مقارنة آلية.
- **مراجعة عدائية:** نموذج آخر يبحث عن: شاهد لا يدعم المنهج، منهج مخلوط (حديث مقابل قول تابعي)، حاشية محقق نُسبت للمؤلف، إسرائيليات لم تُعلَّم.
- **عند الخلاف:** الحكم الأشد (`specialist`) حتى يحسمه نص حرفي أو المتخصص.
- **نتيجة كلها اتفاق = علامة شك** لا نجاح.
- **الأرقام:** تُعرض «أعداد توجيه وليست دقة»، بلا نسب.
- **ممنوع:** إنشاء أو وسم أي اعتماد آلياً. الاعتماد للمتخصص البشري فقط، عبر واجهة المراجعة (بوابة المقارنة بالمصدر + فحص الحدود).
